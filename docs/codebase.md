- Go 1.25+

## Architecture

### 3-Layer Architecture

```
┌─────────────────────────────────────────────┐
│           Interface Layer                   │
│  ┌─────────────────┐  ┌─────────────────┐   │
│  │  API Handlers   │  │   MCP Tools     │   │
│  └────────┬────────┘  └────────┬────────┘   │
└───────────┼────────────────────┼────────────┘
            │                    │
            ▼                    ▼
┌─────────────────────────────────────────────┐
│           Business Logic Layer              │
│              internal/logic/                │
│        (Protocol-independent, shared)       │
└─────────────────────┬───────────────────────┘
                      │
                      ▼
┌─────────────────────────────────────────────┐
│              Data Access Layer              │
│            internal/db/postgres/            │
│             (sqlc generated)                │
└─────────────────────────────────────────────┘
```

### Layer Responsibilities

**Interface Layer** (`api/handlers/`, `mcp/tools/`)

- Request parsing and validation format
- Authentication context extraction
- Response formatting
- Error transformation
- Logging

**Business Logic Layer** (`logic/`)

- Input validation (business rules)
- Domain operations
- Data transformation
- Database calls via queries
- DO NOT log in logic layer

**Data Access Layer** (`db/postgres/`)

- Type-safe SQL queries (sqlc generated)
- Transaction management

## Key Design Principles

- The logic layer should be protocol-independent and can be shared via any interface.
- Use `Input` or `Output` suffix for types in logic layer.
  - DO NOT use protocol-specific suffixes like `RequestBody`/`ResponseBody`,  
    except for external services (because they're already protocol-specific).
- All DB queries are generated by [sqlc](https://sqlc.dev).
  - DO NOT edit the generated files or edit/create the DB-related code in `internal/db/postgres/`.
  - Edit the schema and query in `internal/db/postgres/sql/` and run `sqlc generate`.
- All errors should be defined in `internal/constants/errors.go`.
  - DO NOT use `fmt.Errorf` or `errors.New` directly.
- Basic, and common logics are defined in `github.com/BeaverHouse/go-common`, my public Go library.
  - ALWAYS consider this first.
- (Optional) Auth logics are defined in `gitlab.com/tiny-clover/auth`, my private Go library in GitLab.
  - ALWAYS use this in auth related logics.
- Use other helper functions or existing code as much as possible.
- Always maintain a consistent structure and avoid code duplication.
- Always try to write self-explanatory, human-readable code.
- Only write comments when it is necessary and critical. Allowed examples are:
  - For `go doc`
  - For explaining the complex logic (= it's super hard to understand without comments)

For specific code examples, see the codebase itself.
